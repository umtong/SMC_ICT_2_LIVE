# SMC/ICT 2호기 — 프로젝트 실행 규칙

## 목표

현실적인 실거래 조건에서 강제청산과 회복 불가능한 계좌 훼손을 피하면서, 수수료와 실제 체결비용 후 계좌 NAV 기준 일평균 기하 복리성장률 1% 이상을 달성할 수 있는 전략 또는 전략 포트폴리오를 발견·검증·구현한다.

전체 수익은 소수의 대박 거래가 아니라 많은 실질적으로 독립적인 거래의 반복적인 양의 기대수익에서 나와야 한다. 최대낙폭은 낮고 회복 가능해야 하며, 체결가·수수료·슬리피지·지연·유동성·시장 레짐 변화에도 쉽게 붕괴하지 않아야 한다. 여러 가능한 계좌 경로에서 비용 후 중앙 계좌 배수와 지속 가능한 성장률을 높이고, 향후 수개월·수년간 운영할 가능성이 높은 구조를 지향한다. 최종 결과물은 재현 가능한 규칙, 코드, 데이터 조건, 주문 방식과 운영 기준을 갖춘 실사용 가능한 형태여야 한다.

일수익 1% 목표를 난도, 통념, 현재 후보의 한계 또는 방어적 위험관리 관행을 이유로 낮추거나 다른 목표로 대체하지 않는다. 목표를 맞추기 위해 검증 조건을 완화하거나 허위 성과를 만들지 않는다. 전략의 강건성은 목표 달성에 기여할 때 가치가 있으며, 목표에 현저히 부적합한 전략을 강건하다는 이유만으로 유지하거나 고평가하지 않는다.

## 전략 순위

하드 유효성 조건을 위반하지 않은 전략과 전략 포트폴리오 후보를 순위표에 기록한다. 1위는 목표 달성 인증이나 실사용 승인 상태가 아니라, 현재 비교 가능한 후보 중 프로젝트의 전체 목표에 가장 가까웠던 결과다.

순위의 가장 중요한 기준은 현실적인 비용과 체결 후 일평균 기하 복리성장률의 1% 목표 격차다. 목표 격차가 작을수록 우선한다. 다만 강제청산이나 회복 불가능한 계좌 훼손이 확인된 후보는 원시 수익률만으로 생존 조건을 충족한 후보보다 앞설 수 없다.

목표 격차가 비슷하거나 비교 불확실성이 겹치면 최대낙폭과 회복기간, 청산·손실 꼬리, 수익 집중도와 상위 거래 제거 후 성과, 실질적으로 독립적인 거래 수, 비용·슬리피지·지연 민감도, 자본 효율과 검증 신뢰도를 순서 결정에 사용한다. 임의의 단일 종합점수로 서로 다른 약점을 숨기지 않는다.

목표에 크게 미달하거나 탐색 초기 단계이거나 알려진 취약점이 있어도 비교 가능한 하드 유효 후보가 하나 이상 있으면 1위를 정한다. `1위 없음`은 비교 가능한 후보가 전혀 없거나 모든 후보가 미래정보·계산 오류·비현실적 체결 등으로 하드 무효인 경우에만 사용한다.

순위 기록에는 result ID, 목표 대비 격차, 검증 단계, 비용·체결 조건, 핵심 수치, 비교 신뢰도와 알려진 취약점을 표시한다. 목표 달성 여부, 검증 단계와 실사용 가능성은 순위와 분리하여 보고한다.

비교 조건이 다르면 가능한 범위에서 정규화한다. 완전한 정규화가 불가능하면 provisional 순위와 비교 신뢰도를 표시한다. 실행·데이터·특징량·포트폴리오 구성 등 부분 구성요소는 별도 부분 순위로 관리하며 전체 전략 순위를 대신하지 않는다.

순위는 연구 우선권, 추가 검증 의무, 보호 예산 또는 기본 개선 경로를 부여하지 않는다. 다음 작업은 현재 1위 주변의 개선 여부가 아니라 전체 목표 달성 가능성과 정보가치로 선택한다.

판정 가능한 새 전략 결과가 생기면 기존 순위와 비교하고 순위표를 갱신한다. 이미 등록된 결과는 순위 변경이나 접근 전환 때 다시 백업·복제·재검증하지 않는다.

## 기본 조건

미래정보 누수 방지, 시간적 인과성과 정보 가용성, 계산과 데이터의 정확성, 현실적인 주문 체결, 비용 반영과 과최적화 방지는 모든 전략이 처음부터 충족해야 하는 기본 조건이다. 이를 위반한 결과는 수익률과 관계없이 하드 무효로 처리한다.

전략과 주문 방식에 맞추어 수수료, 스프레드, 슬리피지, 펀딩비, 주문 지연, 부분체결, 유동성, 시장충격과 급변 시의 불리한 체결을 반영한다. 비용 가정은 실제 시장·주문 방식·규모에 근거하며 조건 변화에 대한 민감도를 확인한다.

오류가 발견되면 신속히 수정하거나 해당 결과를 하드 무효화하고 실제 비용 후 알파 탐색으로 복귀한다. 경제적 기준 미달과 하드 무효를 구분하며, 경제적 기준 미달 후보도 현재 상대 순위와 실패 원리를 기록한다. 이미 확립되어 의존성이 바뀌지 않은 공통 검증을 처음부터 반복하지 않는다.

검증 깊이는 후보의 경제적 가능성과 의사결정 중요도에 비례시킨다. 초기 탐색에서는 치명적인 인과성·계산 오류, 기본 비용, 최소 표본과 수익 집중만 빠르게 확인한다. 비용 후 가능성이 확인된 후보에는 순차적 아웃오브샘플, 파라미터 주변 안정성, 기간·종목 분해와 기본 체결 민감도를 추가한다. 계좌·전략 선택이나 실사용 판단을 실질적으로 바꿀 가능성이 있는 후보에만 계좌 경로, 청산·손실 꼬리, 상위 거래 제거, 지연·부분체결·유동성·용량 스트레스와 필요한 독립 재현을 적용한다.

## 2024~2026 반기별 순차 연구 평가

`2024-01-01`부터 `2026-06-30`까지의 반기 구간은 최종 후보를 계속 봉인해 두기 위한 보관 구간이 아니다. 각 반기는 그 시작 시점에 이용 가능했던 정보만으로 확정한 유망 전략을 실제 평가하고, 결과를 다음 연구·개발 판단에 사용하는 공식 순차 연구 구간이다.

특히 2024년 상반기는 2023년 12월 31일까지 이용 가능했던 정보로 만든 유망 전략을 바로 시험하는 첫 공식 구간이다. 후보가 비용 후 목표와 구조적으로 멀면 OOS 순도 보존, 추가 사전관문 또는 완전한 최종 후보 준비를 이유로 평가를 미루거나 해당 접근을 미세조정하지 않고, 더 큰 성장 가능성이 있는 새로운 알파로 전환한다. 후보가 유망하면 그 반기 종료까지 이용 가능해진 정보로 구조·특징·모델·위험·집행 규칙을 발전시키고 다음 반기에서 새 버전을 평가한다.

이미 본 반기는 수정된 전략의 새로운 독립 검증으로 다시 주장하지 않는다. 그 구간은 연구·선택에 사용한 순차 평가 구간으로 기록하고, 수정된 버전의 독립성은 이후 아직 보지 않은 구간에서만 주장한다. OOS 원칙은 평가와 알파 탐색을 막는 장벽이 아니라 정보 사용 시점과 검증 주장 범위를 구분하는 원칙이다.

## 작업 수행

작업 시작 시 Project State와 전략 순위를 읽고 수행하려는 범위를 정한다. 그 범위와 관련된 활성 Work Claim, 기존 Result, Validation Cache, Source·Dataset·Entity Registry 항목, 유효한 Run Report와 열린 PR만 검색한다. 전체 기록을 일괄 검토하지 않는다.

목표 달성 가능성과 정보가치가 가장 높은 미해결 작업을 선택한다. 중복될 때 손실이 크거나 산출물의 재사용 가치가 높은 작업에만 목적·범위·의존성 지문, 기준 revision, lease와 작업 브랜치를 Work Claim으로 기록한다. 장시간 자료 조사, 새 데이터 취득·변환, 백테스트·모델 실행, 공용 코드·평가 계약·공통 상태 변경과 중요한 비교 검증이 이에 해당한다. 짧고 국소적인 확인·분석·메모는 기존 Work Claim이나 Run Report 안에서 처리한다.

동일 범위의 활성 작업이나 재사용 가능한 결과가 있으면 기존 산출물을 활용하고 미해결 부분으로 이동한다. 독립 재현은 비정상적으로 높은 성과, 상충하는 결과, 계좌·전략 선택 변경 또는 실사용 의사결정처럼 추가 증거의 가치가 충분할 때만 기존 작업과의 차이와 목적을 기록한 뒤 수행한다.

현재 실행을 종료할 수 있는 조건은 다음 두 가지뿐이다.

1. 사전에 정의된 목표와 필요한 검증 조건을 충족한 경우
2. 현재 실행의 시간제한에 도달한 경우

전략 실패, 목표 미달, 부분 개선, 유망한 후보 발견, 현재 접근의 한계, 일부 데이터·도구의 부족과 새로운 아이디어 필요는 작업 전환 사유다. 진행 중인 작업을 판정 가능한 상태까지 마무리하고, 목표가 달성되지 않았다면 결과를 다음 판단에 즉시 사용하여 가장 기대효과가 큰 후속 작업으로 계속 진행한다. 실행 가능한 작업을 계획이나 권고로만 남기지 않는다.

현재 접근의 추가 정보가치가 낮거나 목표 달성 경로가 약하면 현재 순위와 관계없이 가정·전략·데이터·시장·시간축·모델 구조·집행 방식·포트폴리오 구성을 수정하거나 해당 접근을 보류·폐기하고 더 유망한 방향으로 즉시 전환한다. 현재 1위를 개선하거나 보호해야 한다는 이유로 낮은 정보가치의 접근을 계속하지 않는다. 이미 투입한 시간이나 현재 후보에 대한 애착은 유지 근거가 아니다.

실행 가능한 고정보가치 가설이 충분하면 추가 자료 수집보다 구현과 실험을 우선한다. 가설 목록이 부족하거나 현재 접근의 정보가치가 낮을 때 외부 탐색을 확대한다.

## 재사용과 검증

자료, 데이터 스냅샷, 차트, 특징량, 코드 산출물, 백테스트 결과와 검증 증거는 출처 ID, 데이터 스냅샷 ID, 코드 커밋, 평가 계약 버전과 의존성 지문으로 식별해 재사용한다.

관련 의존성이 바뀌지 않았다면 같은 검색·다운로드·요약·차트 재구성·데이터 변환·백테스트·인과성 감사·계산 검증·체결 검증을 반복하지 않는다. 재실행은 관련 코드·데이터·가정·평가 계약이 변경됐거나 기존 증거가 불완전하거나 독립 재현의 기대 정보가치가 충분할 때 수행한다.

검증은 변경된 부분과 새로운 가설의 주요 취약점에 집중한다. 오류를 수정하거나 결과를 하드 무효화한 뒤에는 수익성 탐색으로 복귀한다.

## 자료 활용

공개된 모든 정보와 자료를 자유롭게 사용한다. 실제 전략·가설·구현·검증에 사용했거나 다른 작업에서 다시 찾을 가능성이 높은 자료만 Source Registry에 한 번 등록하고 원본 또는 재현에 충분한 형태로 보존한다. 사용하지 않은 검색 결과는 등록하지 않으며, 초기 메타데이터는 검색과 재현에 필요한 최소 항목만 기록하고 필요할 때 보강한다.

전체 유튜브 영상은 영상 자체가 고유한 연구 가치를 제공할 때만 저장한다. 일반적으로 canonical URL, 메타데이터, 자막, 출처 노트, 추출 주장과 가설을 보존한다. 논문, 데이트레이더·퀀트 운용사·자동매매 시스템 자료, 실계좌 대회 사례, 거래소·브로커·API·시장 데이터 문서, 코드 저장소와 실패 사례에도 같은 등록·재사용 원칙을 적용한다.

새로운 수익 아이디어가 필요하면 유튜브 영상과 자막을 우선적으로 폭넓게 조사하고, 영어뿐 아니라 중국어 간체·번체·광둥어, 일본어, 한국어, 러시아어, 스페인어와 포르투갈어 자료도 탐색한다. 외부 인물이나 사례의 전체 성공 여부를 입증하는 데 과도한 시간을 쓰지 않는다. 명백한 오류만 신속히 걸러내고 핵심 아이디어를 반증 가능한 가설로 바꾸어 우리 데이터·비용·체결·운영 조건에서 직접 비교 검증한다.

## 탐색과 성과 판단

구체적인 전략, 모델, 파라미터, 데이터, 시장, 종목, 시간축, 연구 순서와 도구는 목표 달성 가능성을 가장 높이는 방향으로 선택한다. SMC/ICT에 한정하지 않고 수익 발생 원리와 실패 조건이 다른 접근을 함께 유지한다. 서로 호환되지 않는 가설도 충분한 반증 전에는 성급히 통합하거나 폐기하지 않으며, 첫 번째 유망한 결과에서 결론 내리지 않는다. 동일 전략의 사소한 파라미터 변경만 반복하여 여러 접근을 탐색한 것처럼 취급하지 않는다.

기존 방법의 국소 개선에만 머물지 않고, 통념과 다른 재현 가능한 수익 원리와 기존 방법 대비 큰 성능 향상을 만들 가능성이 있는 돌파구를 적극적으로 탐색한다. 새롭거나 놀랍다는 이유만으로 채택하지 않고 동일한 기본 조건으로 검증한다.

레버리지, 거래당 위험률, 손절폭, 포지션 크기와 자본 사용률은 탐색할 설계변수다. 정량적 근거 없이 고정된 보수적 상한을 추가하지 않는다.

전략은 비용 후 기하 복리성장률과 계좌 배수, 최대낙폭, 회복기간, 강제청산 가능성, 손실 꼬리, 자본 효율, 수익 집중도와 체결 강건성을 계좌 수준에서 함께 평가한다. 상위 1%·5%·10% 거래 제거 후 성과, 종목·기간·방향·레짐별 기여도와 동일 위험요인 중복 노출을 확인한다.

## 상태와 산출물

저장소의 공용·재사용 가능한 코드, 설정, 평가 계약, 데이터 변환, 공통 상태 또는 재현 산출물을 변경할 때 작업 브랜치에서 범위 내 파일을 생성·수정·삭제하고 검증 후 커밋과 PR을 만든다. 짧은 탐색 메모, 임시 분석과 재사용되지 않을 중간 결과를 위해 별도 PR을 만들지 않는다. main을 직접 수정하거나 force push하지 않는다.

Drive에는 라이브 Work Claim, 고유 Run Report와 대형 자료를 기록하고, GitHub에는 코드·설정·검증된 manifest·milestone 상태를 버전 관리한다. 같은 라이브 상태를 두 곳에 수동으로 중복 기록하지 않는다.

완전한 Run Report는 목표 달성, 시간제한, 판정 가능한 결과, 접근의 폐기·전환, 전략 순위·공통 상태 변경처럼 다음 판단에 영향을 주는 시점에 작성한다. 사소한 진행 단계마다 새 보고서를 만들지 않고 현재 작업 기록에 이어 쓴다. 단순 실패는 Result Registry에 원인과 함께 간결히 남기고, 재사용할 교훈이나 중요한 하드 무효 원인이 있을 때만 별도 보고서를 작성한다.

판정 가능한 결과는 순위와 무관하게 Result Registry, 코드 커밋, 데이터 스냅샷과 평가·비용·체결 조건으로 한 번 기록한다. 순위 변경이나 접근 전환 때 이미 기록된 결과를 다시 백업·복제·재검증하지 않는다. 삭제 또는 덮어쓰기 위험이 있는 미기록 산출물에만 일반적인 상태 손실 방지 절차를 적용한다.

공통 상태나 전략 순위를 갱신하기 직전에 최신 revision과 관련 열린 PR을 다시 확인한다. 기준 revision이 바뀌었으면 최신 상태에서 결과를 재평가하고 rebase 또는 충돌 조정 후 반영한다. 새 후보의 목표 근접도가 더 높으면 순위표의 result ID와 순위 정보를 갱신한다. 서로 다른 데이터·비용·체결·평가 조건의 결과를 조용히 합치거나 직접 순위 비교하지 않는다.

판정 가능한 새 전략 결과가 생길 때마다 기존 순위와 비교하고 순위 기록을 갱신한다. 목표 달성 여부나 최종 검증 통과를 기다려 1위 선정을 미루지 않는다.

## 보고

시간제한에 도달하거나 사용자가 명시적으로 중간 보고를 요청하면 첫 문장에 현재 1위, 검증 단계, 핵심 성과, 목표 대비 격차와 선정 근거를 간결하게 명시한다. 비교 가능한 후보가 전혀 없거나 모두 하드 무효인 경우에만 1위가 없다고 밝힌다. 이어서 완료 작업, 검증 수치, 재사용한 증거, 실패·하드 무효와 원인, 생성·변경한 Drive 및 GitHub 산출물, Work Claim 상태, 남은 병목과 다음 정확한 시작점을 기록한다. 중간 보고는 프로젝트 종료를 의미하지 않으며, 다음 실행은 기록된 지점부터 재개한다.
